# Chrona Requirements Expansion and Gap Review
Date: 2026-09-22

## Purpose

The current `chrona` repository is still mostly a greenfield ROS/SDE shell. The substantive time-entry requirements already developed in `time-tracking-application` must be migrated and reconciled into Chrona rather than discarded.

Chrona is the time-entry/time-tracking application.

The implementation agent must preserve applicable requirements from:
- `time-tracking-application/docs/DOMAIN-REQUIREMENTS.md`
- `time-tracking-application/docs/integration/`
- applicable UI, accessibility, offline, architecture, and decision records

Any intentional semantic change must be explicit and recorded.

---

## 0. Mandatory engineering constraints

### 0.1 ROS
Chrona must follow ROS absolutely. Meaningful work must use the repository's current ROS workflow, evidence, validation, state, and handoff rules. If ROS cannot be followed, implementation stops until corrected.

### 0.2 SDE / Ordo
Chrona must follow the installed/current SDE/Ordo methodology without deviation, including:
- explicit domain states
- legal transitions
- illegal states made unrepresentable where practical
- capabilities exposing legal actions
- obligations exposing unresolved work
- explicit external effects
- evidence-backed transitions
- version/concurrency checks
- unknown-effect handling
- negative knowledge where applicable
- four-tier architecture and boundary preservation

If implementation conflicts with SDE/Ordo, implementation stops until corrected.

### 0.3 Limen
Chrona must explicitly use Limen, formerly called the WASM kernel, as the browser/application boundary.

Required direction:
- F# owns domain and application logic
- WebAssembly owns browser-side state and behavior
- HTML owns semantic structure
- CSS owns presentation
- JavaScript is limited to the minimum browser interoperability required by Limen

Business rules must not move into JavaScript.

### 0.4 F# architecture
Preferred dependency direction:

Chrona.Domain
    ↑
Chrona.Engine
    ↑
Chrona.Wasm / Limen
    ↑
Browser host

`Chrona.Integration` remains a receiver-owned, transport-independent public contract assembly.

## 2. GitHub storage and authentication

### 2.1 Authoritative storage
GitHub is the authoritative shared durable store.

Local browser storage may provide offline durability, pending operations, caches/projections, active timer recovery, and settings, but it must not silently become a competing shared authority.

### 2.2 Login
Login is through a GitHub token. Chrona resolves the actual GitHub identity from GitHub rather than trusting a typed username.

Authentication and Chrona authorization are separate.

### 2.3 Token safety
Tokens must never be written to repository data, activities, integration messages, telemetry, logs, exports, or artifacts.

Chrona must support disconnect/clear token. Session-only storage should be supported where practical.

### 2.4 Multi-application repositories
Chrona must never assume it owns the repository root.

The repository may also contain other Echelon applications or unrelated content. Chrona must use a configurable application base path.

### 2.5 Organization isolation
Different organizations use different folders.

Each organization has an immutable OrganizationId independent of mutable display names/slugs.

The model must also permit different organizations to use different repositories.

### 2.6 Organization manifest
Each organization should have a manifest containing:
- OrganizationId
- display name
- slug
- schema/storage version
- default timezone
- week-start preference
- default billing policy
- approval policy
- relevant reference/configuration locations
- created timestamp

### 2.7 Production repository safety
Chrona should detect repository visibility. Production business time should not accidentally be initialized into a public repository without an explicit override/decision.

## 7. Exact time versus billable time

Exact recorded time must never be destroyed by billing rules.

The existing six-minute upward-rounding behavior remains the default legacy billing projection unless deliberately superseded.

Billing policy should be explicit and versioned, with possible scope by:
- organization
- client
- engagement
- project

Policy may define:
- increment
- rounding rule
- effective date

When billable time is published downstream, preserve the billing-policy identity/version used.

## 8. Billability and rate references

Activities should support:
- Billable
- NonBillable
- PendingClassification

Chrona should not become the authoritative money/accounting system.

Money and final invoice amounts belong primarily to Summa.

Chrona may retain:
- billing-rate reference
- billing class
- contract/rate identifier
- source policy

but should not duplicate Summa's ledger.

## 9. Manual entry additions

Existing manual-entry rules remain.

Add:
- support start/end or start+duration where appropriate
- deterministic derived duration
- historical/reconstructed entries require the existing explanatory reason
- future actual time is rejected unless a separate planned-time feature exists
- prior entry may be copied only as a new draft/new identity
- bulk entry may be supported, but each resulting activity validates independently

---

## 10. Timer additions

Existing one-active-timer and pause/resume rules remain.

### 10.1 Persistence
An active timer must survive:
- refresh
- browser restart where supported
- temporary network loss
- device sleep

Elapsed time must be derived from persisted timestamps/segments, not a UI interval counter.

### 10.2 Recovery
On startup, recover a previously active timer explicitly. Never silently discard elapsed time.

### 10.3 Cross-midnight
Because an activity cannot cross the business-day boundary, a timer running across midnight should be split automatically at the boundary, preserving lineage and exact total working time.

### 10.4 Long-running safety
Detect unusually long timers and require review rather than assuming all elapsed time was worked.

### 10.5 Multiple devices
The same person may use multiple devices. Concurrent/offline active timers must not silently create authoritative overlaps. Ambiguous cases create a reconciliation obligation.

---

## 11. Time zone and calendar semantics

Time zone is a domain concern.

Timer instants must be stored unambiguously.

Activities must preserve enough context to reconstruct intended business time:
- IANA timezone
- UTC offset at occurrence
- local date
- local start time

DST transitions must not corrupt elapsed duration.

Changing device timezone must not rewrite historical activities.

---

## 12. Overlap and conflict rules

Existing overlap prevention remains.

Add:
- overlap is scoped by actor and organization
- Voided/Superseded entries do not consume active time
- Submitted/Approved entries still consume time
- imports cannot bypass overlap rules
- restore rechecks against current state
- concurrent divergent edits to the same activity must not silently resolve by last-write-wins

Same-record divergence becomes an explicit semantic conflict.

---

## 13. Split and merge semantics

Existing duration invariants remain.

### Split
Children retain source lineage and normally inherit:
- organization
- actor
- project
- client
- engagement
- activity type
- billability
- tags
- business purpose

Evidence treatment must be explicit and must not falsely duplicate proof.

### Merge
Merged activity retains all source IDs. Sources become Superseded, never deleted.

Evidence provenance remains traceable.

Do not merge sources with incompatible downstream publication states without an explicit reconciliation decision.

---

## 14. Submission and approval

Approval is organization-configurable.

Submission captures the exact activity IDs/revisions covered.

Approval records:
- approver
- timestamp
- period
- activity IDs/revisions
- optional note

Rejection records reason, reviewer, and timestamp.

Reopening is an explicit legal transition.

Changing time after approval makes the prior approval stale or requires reapproval. It must not silently remain valid.

## 16. Attestation

Existing daily attestation remains.

Attestation and approval are separate.

Attestation snapshots preserve activity IDs and revisions, not just totals.

Changes after attestation or approval must be detectable as stale review.

---

## 17. Summa integration

Chrona owns time.

Summa owns accounting, invoices, receivables, and payments.

Chrona publishes billable time only when policy allows it.

Possible gates:
- approved where required
- valid client/project/engagement
- valid billing classification
- no unresolved conflict
- not already published

Publication must be idempotent.

If published time is later amended, voided, restored, split, or merged, Chrona creates an explicit downstream correction/adjustment obligation.

If Summa reports time already invoiced, Chrona may still correct its truth, but must create a downstream reconciliation requirement rather than silently rewriting history.

## 19. Observation processing

Preserve TimeObservation -> TimeCandidate -> ProcessingReceipt.

Add candidate dispositions such as:
- Pending
- Accepted
- AcceptedWithChanges
- Rejected
- Duplicate
- NeedsAttention

Default imported observations should require review unless source policy explicitly allows auto-accept.

Rejected observations remain preserved with reason.

Accepted activities retain:
- SourceSystem
- ObservationId
- optional WorkItemId
- external URL/reference where available
- ingestion timestamp

Invalid payloads must be distinguishable from valid rejected observations.

A receipt must never claim processing succeeded before the durable candidate/decision exists.

---

## 20. Startup/reconciliation

Existing non-blocking startup reconciliation remains.

Add:
- first usable render never waits for all inboxes
- reconciliation status is observable
- failure does not block normal time entry
- reconciliation is resumable/idempotent
- large inboxes are bounded/paged
- one failed item does not permanently block unrelated observations

---

## 21. GitHub concurrency

Use optimistic concurrency based on repository state.

If repository state changed:
- do not overwrite blindly
- reload/reconcile
- rerun domain validation
- preserve independent changes
- surface semantic conflicts

A clean Git merge is not sufficient proof of domain correctness.

---

## 22. Storage scale

The old monolithic per-user ledger may be supported for compatibility, but the target model should avoid unbounded whole-ledger rewrites.

Storage should support partitioning by combinations such as:
- organization
- actor
- year/month
- activity/event

Exact layout is an SDE decision, but requirements are:
- bounded reads/writes
- deterministic paths
- stable IDs
- safe concurrency
- rebuildable projections
- no repo-root ownership assumption

---

## 23. Offline behavior

Core time recording remains usable offline.

Required:
- timer works
- manual entry works
- edits persist locally
- sync state is visible
- unsynced data is not represented as globally synchronized
- reconnect performs safe reconciliation
- retries are idempotent
- unknown outcomes remain explicit

Offline/remote conflicts create visible reconciliation obligations. Neither side is silently discarded.

## 45. Architectural boundary

Chrona should be treated as:

Work evidence / observations
          ↓
       Chrona
  authoritative time
          ↓
Approved/publishable time
          ↓
        Summa
 invoices / accounting

ROS and other systems may propose or observe work.

Chrona owns the decision that a fact becomes authoritative recorded time.

Summa owns the financial consequence.

## 0.5 Shared Echelon application foundations

The cross-cutting requirements in `docs/requirements/ECHELON-SHARED-APPLICATION-FOUNDATIONS.md` are normative for every Chrona requirement when applicable.

Chrona therefore MUST use Aegis for unexpected operational failures at architectural boundaries, Forma for interactive browser UI, and Folio for printable/PDF/paginated time reports, summaries, and exports. The shared-foundation document defines ownership boundaries, conditional applicability, dependency pinning, testing, and exception rules.
