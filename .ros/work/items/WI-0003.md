# WI-0003 — GitHub Actions never dispatches a runner

## Observation

Every run of `.github/workflows/ros-validation.yml` has failed, including the
very first push into the repository. Four attempts, all identical:

| Run | Branch | Attempt | Duration | Conclusion |
|---|---|---|---|---|
| 1 (`34789892453`) | `claude/upgrade-echelon-foundry-deps-7uri9c` | 1 | ~3s | failure |
| 2 (`34790954204`) | `claude/upgrade-echelon-foundry-deps-7uri9c` | 1 | ~3s | failure |
| 3 (`34790961424`) | `main` | 1 | ~3s | failure |
| 3 (`34790961424`) | `main` | 2 (re-run) | ~4s | failure |

## Evidence that the job never executed

- The job record carries `runner_id: 0` and an empty `runner_name` — no runner
  was ever assigned.
- The job has no `steps` array at all; not even `actions/checkout` was attempted.
- Log download returns HTTP 404: no logs were ever produced.
- The check run's `output.title`, `output.summary`, and `output.text` are all
  empty strings.

## Evidence that the repository content is not the cause

- `./ros registry check` and `./ros validate` both exit 0 locally at the exact
  failing commit, `94ccd5666744bfd69241b699197ba3aa36c7776d`.
- The workflow YAML is the unmodified bootstrap-managed file and uses only
  standard actions (`actions/checkout@v4`, `actions/setup-node@v4`).
- The failure predates every change made after the initial bootstrap.

## Most likely cause

This repository is private. A job that completes in seconds with no runner
assignment and no logs is characteristically an account-level Actions
condition — an exhausted included-minutes allowance or a reached spending
limit, or Actions disabled by policy — rather than a defect in the workflow or
the repository.

This has not been confirmed: billing and Actions-policy state are not readable
from the agent environment.

## Resolution — 2026-09-14

Resolved by a repository-owner change to GitHub account/repository settings on
2026-09-14. No repository content changed: the first green run is the same
workflow file, on a commit whose only diff from a failing one is this backlog
record.

The diagnosis above is confirmed. The cause was an environment condition
outside the repository, not the workflow or the ROS installation.

First successful run, `34792803744` on `main` at
`a117b1796ee31c890bbde0fd7b2fb00e7156e7e3`:

- a real runner was assigned (`runner_id: 1000008836`), where every failing
  attempt had `runner_id: 0`;
- all eight steps executed, where failing attempts recorded no steps at all;
- `./ros registry check` and `./ros validate` each ran and succeeded on the
  runner, matching their local results;
- duration 13s, against 3-4s for every non-dispatched attempt.

Run `34792802188` on `claude/upgrade-echelon-foundry-deps-7uri9c`, same commit,
also succeeded. Both branches are green.

## Watch item, separate from the above

Once runners dispatch, the final step may still fail on its own merits and has
never been exercised:

```yaml
env:
  ROS_BASE_REF: ${{ github.event.pull_request.base.sha || github.event.before }}
```

On a branch-creation push, `github.event.before` is the all-zero SHA, which is
not a valid base revision for committed-change attribution. Do not pre-emptively
edit this: `.github/workflows/ros-validation.yml` is a bootstrap-managed file
recorded in `.ros/installation.json`, so changing it creates a managed-file
divergence that `ros-bootstrap verify` will report. Resolve it as an explicit
migration if it turns out to be a real failure.

Status as of 2026-09-14: still unexercised, and no longer reachable on `main` or
`claude/upgrade-echelon-foundry-deps-7uri9c` — both branches now exist, so a
push to either carries a real `github.event.before`. The green run confirms the
ordinary push path works. The all-zero case would next appear on the first push
that creates a new branch. Left open as a watch item; no change made.
